# 故事版：餐廳廚房的試吃大會 🍳

> 這篇是**寫給小朋友也看得懂**的故事版。用一個「餐廳開門前，主廚和學徒在廚房裡一道一道試吃」的故事，幫你「感覺」出單元測試、`#[cfg(test)]`、`use super::*`、`assert_eq!` / `assert!`、`#[should_panic]`、`#[ignore]`、回傳 `Result` 的測試、整合測試、doc test、`mockall`、`cargo nextest`、property-based testing。故事裡不講程式名詞，名詞都放在 `>` 小框框和最後的對照表裡。先享受故事，別急著背。

---

## 只在廚房裡的試吃桌

小宇在阿芬主廚的餐廳當學徒。廚房角落有一張**試吃桌**，只有在「**試吃時間**」才會搬出來；正式營業時，試吃桌會收起來，客人完全看不到。

站在試吃桌旁邊，小宇**看得到整個廚房**：不只端出去的菜，連還沒上桌的醬汁、私房調味料都能嘗一口。

> 這就是 **單元測試**：放在同一個檔案末端的 `#[cfg(test)] mod tests { use super::*; ... }`。`#[cfg(test)]` 讓它只在 `cargo test` 時編譯；`use super::*` 讓測試看到外層所有東西，**包括 private 的**（白盒測試）。每道試吃用 `#[test]` 標記。

---

## 跟標準答案比

阿芬給小宇一張**標準答案卡**：

- 「階乘湯」放 5 份料，味道要是 120 分。
- 放 0 份料，味道要是 1 分（空碗也算一份基本味）。
- 「分蛋糕」10 塊分給 3 個人，每人 3 塊。
- 分給 **0 個人**？那一定要回報「**不能這樣分**」。

小宇一道一道嘗，跟卡片比。不對的時候，卡片會清楚寫出「**應該是多少、實際是多少**」。

> 這就是 **斷言**：`factorial_zero` 裡 `assert_eq!(factorial(0), 1)`、`factorial_five` 裡 `assert_eq!(factorial(5), 120)`、`divide_ok` 裡 `assert_eq!(divide(10, 3), Ok(3))`、`divide_zero` 裡 `assert!(divide(1, 0).is_err())`。`assert_eq!` 失敗時會印出左右兩邊的值；`assert_ne!` 則是確認不相等。

## 這道菜「應該」要冒火

有一道「**火焰甜點**」，做法正確的話，最後一定會**轟的一聲冒出火**。

如果小宇做完卻**沒冒火**，那才是做錯了。而且光是冒火還不夠，火焰上要出現「overflow」的字樣，才是這道菜。

> 這就是 **`#[should_panic(expected = "overflow")]`**：`overflow_panics` 這個測試**要 panic 才算通過**，`expected` 會比對 panic 訊息（子字串比對）。

---

## 慢燉的先放一邊

「**五小時燉牛肉**」太慢了，每次試吃都等它，大家會等到睡著。

阿芬在鍋子上貼一張紙條：「**慢，平常先跳過**」。平常試吃不碰它；只有在週末大檢查時，才特別說「今天**連貼紙條的也一起試**」。

> 這就是 **`#[ignore = "slow"]`**：`slow_test` 預設不跑，要跑用 `cargo test -- --ignored`。需要網路、資料庫或特別慢的測試都適合這樣標。

---

## 回報問題，而不是摔盤子

以前小宇做菜，每一步只要不對，他就**直接摔盤子**，整個廚房嚇一跳。

阿芬教他：「你可以照著步驟做，**哪一步出問題就把那一步的狀況交回來給我**，不用摔盤子。最後全部沒問題，就說一聲『好了』。」

> 這就是 **回傳 `Result` 的測試**：`fn parse_chain() -> Result<(), Box<dyn std::error::Error>>` 裡寫 `let n: i32 = "42".parse()?;`，出錯就用 `?` 回傳錯誤（測試失敗），最後 `Ok(())`。比一連串 `unwrap()` 清楚。

## 神祕客來點餐

除了廚房試吃，餐廳還會請**神祕客**來吃飯。神祕客坐在用餐區，**只能看菜單點菜**，看不到廚房，也嘗不到私房醬汁。

他們吃的是客人真正會點的「**一整套餐**」，確認從點餐到上菜整個流程都沒問題。好幾位神祕客要共用的「評分表」，則放在一個**不會被當成神祕客**的資料夾裡。

> 這就是 **整合測試**：`tests/` 下每個 `.rs` 都是**獨立的 crate**，只能用 `pub` API（黑盒測試），例如 `tests/api.rs` 裡 `use my_crate::Client;`。共用 helper 放在 `tests/common/mod.rs`，才不會被當成另一個測試 crate。

## 菜單上的示範照片

菜單上每道菜旁邊都有一張**示範照片和做法說明**。阿芬規定：「照片也要**真的照著做一次**，做出來不一樣就是菜單過期了。」

這樣菜單永遠不會騙人。不過這個規定**只對出版成冊的食譜書**有效；餐廳自己的內部筆記，就不會自動照著做。

> 這就是 **doc test**：`///` 註解裡的程式碼區塊會被 `cargo test` 當測試跑（`cargo test --doc`）。`factorial` 上的 `# Examples` 就是示範。**只有 library crate 會跑 doc test**；本章是 binary，所以只示範語法。還可以標 `ignore`、`no_run`、`should_panic`、`compile_fail`。

---

## 假的供應商

有一道菜要用到「**供應商送來的會員名單**」。可是真的打電話給供應商又慢又貴，名單還每天在變。

阿芬請小宇扮演**假的供應商**，並先說好劇本：「待會有人問 **1 號**是誰，你就回答 **alice**。」這樣就能專心確認這道菜**拿到名單後**有沒有做對。

> 這就是 **mocking（`mockall`）**：在 `trait Db` 上加 `#[automock]` 會產生 `MockDb`；`mock.expect_get_user().with(predicate::eq(1)).returning(|_| Some("alice".into()))` 就是劇本。可以控制參數、次數、回傳值。`mockall` 放在 `[dev-dependencies]`。

## 多開幾個試吃窗口、隨機出題

餐廳生意越來越好，菜越來越多，一個人一道一道試太慢了。阿芬**多開了幾個試吃窗口**，每道菜各自在一個窗口試，誰沒過一目了然。

她還請了一位「**亂點菜的客人**」：隨機點各種奇怪的組合。如果某個組合出問題，他會**一直簡化**，最後告訴你「**最小的出問題點法**」。

> 這就是 **`cargo nextest`** 與 **property-based testing**：`cargo nextest run` 每個測試一個 process 並行，進度 UI 和失敗訊息更清楚。`proptest` / `quickcheck` 會自動產生輸入，找到反例後再縮成最小的例子，對 parser、資料結構特別有用。

## 回到現實：故事 ↔ Rust 對照表

| 故事裡的東西 | 真正的 Rust 概念 |
|------|------|
| 只在試吃時間搬出來的試吃桌 | **`#[cfg(test)] mod tests`** |
| 一道一道試吃 | **`#[test]`** |
| 嘗得到私房醬汁 | `use super::*`，可測 private（白盒） |
| 標準答案卡 | **`assert_eq!`** / `assert!` / `assert_ne!` |
| 階乘湯、分蛋糕 | `factorial`、`divide` |
| 要冒火的火焰甜點 | **`#[should_panic(expected = "overflow")]`** |
| 「慢，平常先跳過」 | **`#[ignore = "slow"]`** |
| 週末連貼紙條的一起試 | `cargo test -- --ignored` |
| 交回狀況而不摔盤子 | 回傳 **`Result`** 的測試 + `?` |
| 只看菜單的神祕客 | **整合測試** `tests/*.rs`（黑盒） |
| 共用評分表的資料夾 | `tests/common/mod.rs` |
| 菜單上的示範照片 | **doc test**（`///` 區塊） |
| 只對出版的食譜書有效 | doc test 只在 lib crate 跑 |
| 照劇本回答的假供應商 | **`mockall`** 的 `#[automock]`、`MockDb` |
| 多開幾個試吃窗口 | **`cargo nextest run`** |
| 亂點菜還會簡化的客人 | **`proptest`** |

## 一句話記住

> **單元測試是廚房裡的試吃桌（看得到私房醬汁），整合測試是只看菜單的神祕客，doc test 是要真的照做一次的菜單照片；用標準答案卡（`assert_eq!`）比味道、慢菜先貼紙條（`#[ignore]`）、外面的供應商就找人照劇本演（`mockall`）。**
