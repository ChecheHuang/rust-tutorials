# 故事版：夏令營的廣播小隊長 📢

> 這篇是**寫給小朋友也看得懂**的故事版。用一個「夏令營廣播小隊長」的故事，幫你「感覺」出依賴注入、trait 當介面、構造函式注入、`Arc<dyn Trait>`、在 main 手動組裝、泛型注入、shaku 容器、Service Locator 反模式，還有用假元件寫測試是什麼。故事裡不講程式名詞，名詞都放在 `>` 小框框和最後的對照表裡。先享受故事，別急著背。

---

## 小隊長只負責「講」

夏令營裡，小樂被選為**廣播小隊長**。他的工作只有一件：每次有消息，就說「**現在幾點幾分，○○○請注意：……**」，然後把消息送到營隊的每個角落。

可是小樂自己**沒有手錶**，也**不會架喇叭**。

他想：「我又不是做手錶的，也不是修喇叭的。我只要會**看時間**、會**對著麥克風講話**就好。」

> 這就是 **把「需要的東西」寫成介面**：程式裡的 `trait Mailer`（會 `send` 訊息的東西）和 `trait Clock`（會 `now_unix` 報時的東西）。`NotifyUseCase` 只在乎「有一個會報時的、有一個會送信的」，不在乎它們是怎麼做出來的。

---

## 開營那天，營長把東西交到他手上

開營典禮上，營長走過來，**親手**把一支麥克風和一個時鐘交給小樂：

「這是喇叭的麥克風，這是大廳的時鐘。從今天起，你就用這兩樣工作。」

小樂沒有自己跑去倉庫翻東西，也沒有自己做一個時鐘。東西是**別人在他上任那一刻交給他的**。

> 這就是 **構造函式注入**：`NotifyUseCase::new(mailer, clock)`。依賴在「建立」的時候從外面傳進來，存在結構體欄位裡。之後 `notify()` 只要用 `self.clock.now_unix()` 和 `self.mailer.send(...)` 就好。

---

## 大家一起看同一個時鐘

大廳的時鐘只有**一個**，但廚房阿姨、游泳教練、小樂都要看它。

營長沒有幫每個人買一個新時鐘，而是讓大家**共用**：誰要用就看一眼，最後一個人離開大廳之前，時鐘都會一直掛在那裡。

而且小樂不知道（也不用知道）那是電子鐘還是指針鐘——只要它**會報時**就行。

> 這就是 **`Arc<dyn Trait>`**：`Arc` 讓好幾個人共用同一份東西（引用計數，最後一個不用了才收掉）；`dyn Clock` 表示「某個實作了 `Clock` 的東西」，具體是 `SystemClock` 還是別的，執行時才決定。`Clock: Send + Sync` 讓它可以安全地在不同執行緒之間共用。

---

## 營長的開營清單

營長手上有一張**開營清單**，一行一行照順序做：

1. 先把喇叭裝好（`StdoutMailer`）
2. 再把時鐘掛好（`SystemClock`）
3. 最後把麥克風和時鐘交給廣播小隊長

清單就寫在營長的本子上，**誰拿到什麼，一眼就看得出來**。如果營長忘了準備時鐘就想派小隊長上任，副營長馬上會說：「等等，時鐘呢？你這樣不能開營！」

> 這就是 **manual wiring（手動組裝）**：在 `manual_demo()`（實務上就是 `main`）裡依序 `Arc::new(StdoutMailer)`、`Arc::new(SystemClock)`，再 `NotifyUseCase::new(mailer, clock)`。少傳一個參數，**編譯器**就不讓你過。沒有魔法，IDE 跳轉、重構都好用——這是 Rust 最推薦的做法。

---

## 另一種做法：指定專用的那一支

隔壁營隊的營長比較講究。他不說「給你**某一支**麥克風」，而是在上任狀上直接寫明：「你用的就是**這一型號**的麥克風。」

這樣小隊長拿起來就知道每個按鈕在哪，講話**一點延遲都沒有**。可是如果哪天想換別的型號，就得重新發一張上任狀。

> 這就是 **泛型注入**：`struct UseCase<R: Repo> { repo: R }`。編譯期就把具體型別定死（monomorphization），零成本、最快；代價是型別會跟著變成 `UseCase<R>`，要換實作或混著放比較麻煩。至於 web 程式，axum 的 `State<AppState>` 也是同一個想法：把共用的依賴放進 `AppState`，每個 handler 從那裡拿。

---

## 自動配發中心

後來夏令營越辦越大，有好幾十個小隊長、好幾十種器材。營長的清單寫得手好痠。

於是營隊做了一個**自動配發中心**。每樣器材上都貼一張標籤：「**我是一支麥克風**」。每個小隊長的名牌上也寫著：「**我需要一支麥克風**」。

配發中心在**開營前**就把標籤對好；只要有人需要的東西沒人提供，開營前就會被擋下來，不會等到典禮上才出糗。開營後，小隊長只要去櫃台說「我是通知員」，就能領到配好器材的自己。

> 這就是 **shaku 容器**：`#[derive(Component)]` + `#[shaku(interface = MailerSvc)]` 是貼在器材上的標籤；`NotifierImpl` 裡的 `#[shaku(inject)] mailer: Arc<dyn MailerSvc>` 是名牌上的「我需要」；`module! { AppModule { components = [PrintMailer, NotifierImpl], ... } }` 是配發中心；`AppModule::builder().build()` 開營，`module.resolve_ref()` 領出 `&dyn Notifier`。shaku 在**編譯期**用 macro 檢查依賴圖，不像 Java Spring 在執行時才發現少東西。

### 什麼時候才需要配發中心？

營長說：「我們營只有五六個小隊長，清單寫一寫就好。等到**三十個以上**、還要分『正式營』『試營』兩套器材的時候，再來用配發中心。」

> 這就是 **什麼時候用 DI 框架**：元件多、依賴圖深、要多套組態或生命週期管理時才考慮。一般 microservice 用手動組裝就夠，框架是備胎。

## 不要自己去倉庫亂翻

有一個新來的小隊長小芸，營長沒交東西給她。她每次要廣播，就**自己跑去大倉庫翻**：「麥克風呢？時鐘呢？」

結果：

- 沒人知道她到底用了哪些東西
- 倉庫少了一樣，要等她廣播到一半才發現
- 想換一支壞掉的麥克風，得先找出「到底有誰偷偷在用」

營長嘆氣：「東西**一定要在上任時交給你**，不能自己去倉庫拿。」

> 這就是 **Service Locator 反模式**：`GLOBAL_CONTAINER.get::<dyn Mailer>()` 把依賴藏在全域容器裡，看函式簽名看不出它需要什麼，測試也很難替換。永遠在**建構時**把依賴傳進去。

---

## 演練日：假時鐘和玩具麥克風

正式開營前，營隊要**演練**。營長不想真的把喇叭打開吵到附近鄰居，也想看看「如果現在是半夜 12 點，小隊長會怎麼講」。

於是演練時，營長交給小樂的是一支**玩具麥克風**（只把講的話記在本子上）和一個**停在 12:00 的假時鐘**。

小樂完全沒發現差別，照樣說：「現在 12:00，請注意……」營長翻開本子一看，就知道他講得對不對。

> 這就是 **用假實作測試**：寫一個 `impl Clock for FrozenClock`，或 `InMemoryRepo` 之類的假東西，在測試裡 `NotifyUseCase::new(Arc::new(fake_mailer), Arc::new(frozen_clock))`。因為依賴是從外面傳進來的，換成假的完全不用改小隊長本人的程式碼。

---

## 營長的三個叮嚀

1. **只有一種的東西，不用硬貼「我是某種麥克風」的標籤。** 真的會換的才需要介面。
2. **別替時鐘再包一個上鎖的箱子。** 時鐘本來就能大家一起看，多一把鎖只會讓大家排隊。
3. **兩個小隊長不能互相等對方先上任。** 甲說「乙來了我才上任」、乙說「甲來了我才上任」，那就永遠開不了營。把兩人都需要的東西拆出來，交給第三方準備。

> 這就是 **常見陷阱**：濫用只有單一實作的 trait；`Arc<Mutex<dyn T>>` 多包一層鎖通常不需要，`Arc<dyn T>` 就夠；循環依賴要重構成 `A、B → C`。另外 `Arc::clone(&x)` 比 `x.clone()` 更清楚表示「只是多一個人共用」，不是複製一份。

## 回到現實：故事 ↔ Rust 對照表

| 故事裡的東西 | 真正的 Rust 概念 |
|------|------|
| 廣播小隊長 | **use case**：`NotifyUseCase` |
| 「會送話的」「會報時的」 | **trait 介面**：`Mailer`、`Clock` |
| 喇叭、大廳時鐘 | **具體實作**：`StdoutMailer`、`SystemClock` |
| 上任時營長親手交東西 | **構造函式注入** `NotifyUseCase::new(mailer, clock)` |
| 大家共用同一個時鐘 | **`Arc`** 共享所有權 |
| 只要會報時，不管哪一種鐘 | **`dyn Trait`** 動態分派 |
| 營長的開營清單 | **manual wiring**（在 `main` 組裝） |
| 少了時鐘不准開營 | **編譯期檢查** |
| 上任狀寫死型號 | **泛型注入** `UseCase<R: Repo>` |
| 器材標籤「我是麥克風」 | `#[shaku(interface = ...)]` |
| 名牌「我需要麥克風」 | `#[shaku(inject)]` |
| 自動配發中心 | `module! { AppModule { ... } }` |
| 去櫃台領人 | `module.resolve_ref()` |
| 自己去倉庫亂翻 | **Service Locator 反模式** |
| 玩具麥克風、停住的假時鐘 | **測試用假實作**（fake / in-memory） |
| 兩人互等對方上任 | **循環依賴** |

---

## 一句話記住

> **小隊長不自己找器材，而是上任時由營長親手交給他（構造函式注入）；營長在一張清單上排好誰拿什麼（main 手動組裝），演練時換成假時鐘也不用改小隊長——只有器材多到寫不完清單，才需要自動配發中心（shaku）。**
