# 故事版：麵包店的問題回報單 🥐

> 這篇是**寫給小朋友也看得懂**的故事版。用一個「在家裡開的小麵包店幫忙」的故事，幫你「感覺」出 `Option`、`Result`、`?` 運算子、`From` 自動轉型、自訂錯誤 enum、`unwrap_or` / `ok_or`、`panic!` 是什麼。故事裡不講程式名詞，名詞都放在 `>` 小框框和最後的對照表裡。先享受故事，別急著背。

---

## 打開餅乾罐之前

小柔放學後都到奶奶的麵包店幫忙。奶奶叫她：「去**餅乾罐**拿第一塊餅乾給客人。」

餅乾罐有兩種可能：**裡面有餅乾**，或是**空空的**。奶奶教她：「打開之前，兩種情況都要想好怎麼說。有的話就拿出來；沒有的話，就跟客人說『今天賣完了』。」

> 這就是 **`Option<T>`**：`Some(x)` 有東西、`None` 沒東西。程式裡 `match v.first() { Some(x) => ..., None => println!("empty") }`，兩種都要處理。`v.first().map(|x| x * 2)` 則是「有餅乾就把它變兩倍，沒有就還是沒有」。

---

## 每一件工作都要交回報單

麵包店有個規矩：**每做一件事，都要交一張回報單**。回報單只有兩種：

- 綠色單：「**成功了**，這是成果。」
- 紅色單：「**失敗了**，這是原因。」

小柔把客人寫的「42」唸成數字 42 —— 交綠色單。客人寫的是「oops」——唸不出數字，交紅色單，上面寫「這不是數字」。

奶奶說：「**不可以只交成果、不說失敗。**拿到單子的人一定要看顏色。」

> 這就是 **`Result<T, E>`**：`Ok(T)` 是綠色單、`Err(E)` 是紅色單。`"42".parse()` 回傳 `Result<i32, _>`。跟丟出例外不一樣，失敗是**寫在回傳值上**的，編譯器會逼你處理，不會「忘記檢查就上線爆炸」。

---

## 遇到問題，立刻往上交

奶奶要小柔做「**把客人寫的數字加倍**」這件事。步驟是：先讀數字，再乘以 2。

以前小柔每一步都要寫一大段：「如果讀成功，就繼續；如果失敗，就把紅色單交回去……」好囉嗦。

奶奶教她一個暗號——在每一步後面**畫一個小問號**：

「這一步成功就繼續往下做；**失敗就馬上停手，把紅色單直接交給叫你做事的人**。」

> 這就是 **`?` 運算子**：`parse_and_double` 裡的 `let n: i32 = s.parse()?;`，成功拿到 `n` 繼續；失敗就立刻 `return Err(...)`。`parse_and_double("21")` 得到 42，`parse_and_double("oops")` 直接回紅色單。

---

## 不同部門的紅色單，換成店裡統一格式

麵包店後來越做越大。做「**算庫存**」這件事要兩步：

1. 去倉庫**拿庫存本子**——可能找不到本子（倉庫的問題）。
2. 把本子上的字**讀成數字**——可能字寫壞了（讀字的問題）。

倉庫的紅色單長一個樣子、讀字的紅色單又長另一個樣子。奶奶說：「我只想收**一種**格式的單子！」

於是她做了一張**店裡的統一問題單**，上面有三個勾選框：「□ 倉庫問題」「□ 讀字問題」「□ 找不到東西」。她還貼了一張**換單說明**：「看到倉庫的紅色單，就勾第一格；看到讀字的紅色單，就勾第二格。」

有了換單說明，小問號在交單時會**自動換成統一格式**。

> 這就是 **自訂錯誤 enum + `From`**：`enum AppError { Io(io::Error), Parse(ParseIntError), NotFound(String) }` 是統一問題單；`impl From<std::io::Error> for AppError` 和 `impl From<ParseIntError> for AppError` 是換單說明。`load_count` 裡的 `fs::read_to_string(path)?` 和 `s.trim().parse()?` 都會透過 `From` 自動轉成 `AppError`。

### 單子要能唸給人聽

奶奶又說：「統一問題單要能**用一句話唸出來**，客人才聽得懂。」於是每一格都配一句話：「io error: ……」「parse error: ……」。

> 這就是 **`impl Display for AppError`**（還有 `impl std::error::Error for AppError {}`）：讓錯誤能用 `{e}` 好好印出來。`load_count("nonexistent.txt")` 就會印出 `load err: io error: ...`。

---

## 沒有就用備用的

有時候奶奶不想為小事停下來。

- 「客人寫的數字唸不出來？那就**當作 0** 好了。」
- 「餅乾罐空了？那就給我一張紅色單，寫『**缺貨**』。」

> 這就是 **`unwrap_or` 與 `ok_or`**：`bad.unwrap_or(0)` 失敗就用預設值；`maybe.ok_or("missing")` 把「空空的（`None`）」換成「紅色單（`Err("missing")`）」，從 `Option` 變成 `Result`。

---

## 餅乾罐也能畫小問號

小柔要找「一張紙條上**第一個數字**」。她先找第一個是數字的字；找不到就直接說「沒有」。

> 這就是 **`?` 也能用在 `Option`**：`first_digit` 裡 `s.chars().find(|c| c.is_ascii_digit())?`，找不到就立刻回 `None`。`first_digit("abc12")` 是 `Some(1)`，`first_digit("abc")` 是 `None`。注意：回 `Option` 的函式裡才能對 `Option` 用 `?`。

---

## 火災警報

有一天，烤箱冒出黑煙——這不是「麵包烤失敗」那種小事，是**根本不該發生**的大事。奶奶立刻按下**火災警報**，全店停工，大家先離開。

奶奶說：「紅色單是給**會發生、可以處理**的問題用的，例如客人寫錯字、倉庫找不到本子。火災警報只給**真的出大事、店不能再開下去**的時候用。」

小柔問：「那如果我很確定罐子裡一定有餅乾，可以不看就直接拿嗎？」

奶奶說：「可以，但要是你錯了，就等於按下火災警報。所以最好在旁邊**寫下你為什麼這麼確定**。」

> 這就是 **`panic!` vs `Result`**：`panic!` 是程式有 bug、無法繼續時用；IO、parse、使用者輸入要用 `Result`。`unwrap()` 遇到 `None` / `Err` 會 panic；`expect("理由")` 一樣會 panic，但留下訊息。程式裡 `std::panic::catch_unwind` 只是示範，日常不該拿來當流程控制。

---

## 店長最後收單

一天結束，所有紅色單都會傳到**店長桌上**。店長看一看，把問題唸出來，然後決定今天要不要提早打烊。

> 這就是 **在邊界處理錯誤**：`main` 可以回 `Result<(), Box<dyn std::error::Error>>`，或寫一個 `run() -> Result<(), AppError>`，在 `main` 用 `if let Err(e) = run() { eprintln!(...); std::process::exit(1); }` 統一收尾。

---

## 回到現實：故事 ↔ Rust 對照表

| 故事裡的東西 | 真正的 Rust 概念 |
|------|------|
| 餅乾罐有餅乾 / 空空的 | **`Option<T>`**：`Some` / `None` |
| 有餅乾就變兩倍 | `opt.map(...)` |
| 綠色回報單 / 紅色回報單 | **`Result<T, E>`**：`Ok` / `Err` |
| 拿到單子一定要看顏色 | 編譯器強制處理 `Result` |
| 每步後面畫小問號 | **`?` 運算子**（失敗就早返） |
| 店裡的統一問題單 | 自訂錯誤 **`enum AppError`** |
| 換單說明 | **`impl From<X> for AppError`** |
| 小問號交單時自動換格式 | `?` 會呼叫 `From` 轉型 |
| 問題單能唸成一句話 | `impl Display for AppError` |
| 唸不出來就當 0 | `unwrap_or(0)` |
| 空罐子換成「缺貨」紅色單 | `ok_or("missing")` |
| 找第一個數字，沒有就說沒有 | `Option` 上的 `?` |
| 火災警報，全店停工 | **`panic!`** |
| 不看就直接拿 | `unwrap()` / `expect("理由")` |
| 店長最後收單 | 在 `main` / `run()` 統一處理錯誤 |

---

## 一句話記住

> **可能沒有就用 `Option`、可能失敗就用 `Result`（把失敗寫在單子上）；每步畫個 `?` 讓問題自動往上交，用 `From` 把各種紅色單換成統一格式；只有真的出大事才按 `panic!` 火災警報。**
